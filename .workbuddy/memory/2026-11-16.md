## serial_pair_test 运行失败根因与修复（tester_v158）
- 现象: letter / sort 两种配对模式都判 fail。
- 根因（探针复现证实）: 打开串口后立即发送会丢失开头 1~4 个字符（FTDI 驱动未就绪 + RS485 方向切换；清缓冲 DiscardInBuffer 与到达字节竞争）。配对逻辑本身没问题。
- 修复 serial_loopback_tester.cs `TestPair`:
  1. Open 后加 300ms 稳定延时；
  2. 单方向失败自动重试最多 3 次（间隔 100ms）；
  3. 每次重试清缓冲后等 50ms 再发；
  4. Detail 中 recv 数据去除 \r\n。
- 输出格式: serial_pair_test 的 c 串全部改用 ';' 分隔，不再含逗号。
- **真正的根因（第二轮确认）**: serial_loopback_tester.cs TestPair 接收循环 `recv = rx.ReadExisting()` 是覆盖赋值，而 FTDI 按 16ms 延迟定时器分块上交数据，后半段到达时把前半段覆盖 → 永远匹配失败（fail 样本 recv=def_B 正是"后半段"）。改为 `recv +=` 累加后，连跑 28 轮（sort+letter）全部 pass。之前 300ms 延时+重试只降低了概率，累加修复才是根治。
- 验证: 探针项目 `tester_v158\_serial_probe`（独立 console，引用正式 serial_port_discovery.cs / serial_loopback_tester.cs 副本）回归 28/28 pass，输出无逗号。
- CS1061 真因: 我把字段写成 PnpDeviceID，实际是 PnpDeviceId（大小写），已修正。
- CLI `dotnet build` 有 ~17 个既有 CS0023 错误（无关旧文件，行号甚至超过文件行数），VS 构建正常（17:28 成功出 dll）——用户用 VS 构建即可。

## gpio_set FAIL 根因（hero_aux MCU CLI）
- 用户判断正确: RX 里 "Unknown command. Available: 1 - I2C scan..." 是 **MCU 开机横幅**——MCU 复位瞬间命令字符丢失/被当杂散输入, 复位后打印横幅。
- 连带发现: touch_auto 期望 "DISABLED/ENABLED" 但固件实际回复 "Touch auto-report is OFF. Use '7 1' to enable." → 文案不匹配会误判 fail。
- 修复 ecolab_hero_aux_my_test.cs:
  1. `wait_for_prompt` 加 out promptSeen; `recv_response` 加重载;
  2. `send_and_recv` 复位容错: 检测"无提示符"或响应含 "Unknown command"/"Available:" → 等 1s、清缓冲、重发命令(最多3次); 保持"恒返回 pass、调用方校验内容"的原约定;
  3. touch_auto 接受 "is OFF"/"is ON" 与旧文案并存。
- 疑点待确认: wdt_feed 期望 "STOPPED/STARTED", 若固件文案同样不同会误判; 且若喂狗恢复命令撞上复位窗口丢失, MCU 会周期性复位(约50s)导致后续步骤随机失败——需用户跑一轮完整流程看 wdt 步骤响应文本。
- MCU 串口: COM20 @9600 (setup.ini ecolab_hero_aux_serial_port)。
- 用户指出第三层问题: clear_rx 只清 rxBuf, 驱动层还有未投递的残留字节, DataReceived 事件在 clear 之后补投进来 → 清了等于没清。修复: clear_rx 先 port.DiscardInBuffer() 再 lock 清 rxBuf (两层一起清)。rxLock 本身不是元凶 (持有仅微秒级), 真正问题是清理不彻底的时序窗口。
